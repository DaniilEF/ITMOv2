## 2. Задачи и артефакты (выполнять только пп. 1–2 из README)

  - Каждый файл содержит раздел «Как использовали AI»: назначение запроса, тип промпта, ссылка на строку в `prompts.md`, как проверили результат.

  - Минимально достаточные шаблоны для последующей доработки по пунктам оценки (см. Раздел 4).

- Задача B (п.2 README): довести master prompt до воспроизводимого состояния.
  - Обновить «Master Prompt v1» в `prompts.md` по структуре (Раздел 3), соблюдая OUT-1 и QA-1.
  - Выход помощника в запуске 2 — строго `summary`, `risks` (≤3), `checks`.

## 3. Формат результата AI (OUT-1)

- Структура ответа на один diff:
  - `summary`: краткое описание изменения.
  - `risks`: не больше трёх элементов. Для каждого:
    - `file`, `line`;
    - `candidate`;
    - `evidence` (цитата строки diff) и/или ссылка на правило CASE.md;
    - `rule` (например, OUT-1, SEC-1);
    - `check` (воспроизводимая проверка).
  - `checks`: список запускаемых проверок.

Ограничения:
- Flow: candidate → evidence → check; нет evidence — пропустить риск (QA-1).
- Не более 3 рисков.
- Не придумывать правила; использовать только SEC-1..QA-1 из CASE.md.

## 4. Покрытие критериев оценки (чек-листы)

- Обязательная структура и команды (1 балл)
  - Все файлы из таблицы README присутствуют.
  - В корне репозитория команды `make install` и `make test` выполняются (подтвердить в «Проверках», Раздел 6).

- Контекст AS IS, проблема и метрики (2 балла)
  - `context.md`: описать продукт/роль сервиса, пользователей, процесс AS IS, задействованные системы; сослаться на CASE.md.
  - `problem.md`: сформулировать пользователя, проблему, измеримые метрики успеха (минимум 2 метрики, измеримые и проверяемые).

- TO BE, use cases, user stories, план поставки (2 балла)
  - `analysis.md`: эскиз TO BE-процесса на основе кейса.
  - `product_management.md`: минимум 2 use cases и 2 user stories (скелеты, можно TODO).
  - `project_management.md`: инкременты и роли людей/AI; план поставки (этапы, даты-заглушки).

- ADR, архитектура и связность (2 балла)
  - `adr.md`: одно решение с Mermaid-схемой (скелет) и связностью с контекстом/процессом.

- Tests: unit, integration, load, E2E (2 балла)
  - `tests_*.md`: списки проверок, соотнесённые с правилами CASE.md (например, OUT-1, SEC-1, API-1, REL-1, OBS-1).

- prompts.md: два запуска и собственная критика (1 балл)
  - `P1-01` и `P1-02` заполнены; есть ссылки на строки diff и правила; собственная критика присутствует.

Примечание: пункты TO BE/ADR/Tests будут дорабатываться вручную (пп. 3–5 README). На этапе пп. 1–2 обеспечить минимальные скелеты и связность.

## 6. Рабочий процесс

1) Прочитать `CASE.md`, `TRAINING_PR.diff`, `prompts.md` (P1-01, P1-02, Master Prompt v1) и `context.md`.
2) Задача A: заполнить/синхронизировать обязательные файлы; добавить «Как использовали AI» с ссылками на `prompts.md`.
3) Задача B: обновить «Master Prompt v1» под OUT-1/QA-1; зафиксировать формат результата и ограничения.
4) Вставить в контекст примеры «хорошего»/«плохого» комментария из CASE.md.
5) Подготовить минимальные правки без избыточных комментариев.

Остановка: если риск нельзя подтвердить строкой diff или правилом (QA-1), не включать его в `risks`; при отсутствии подтверждений вернуть только `summary` и пустые `risks`/`checks` и эскалировать вопросы человеку.

## 7. Проверки и evidence

- Для каждого риска указать `file:line`, цитату из diff (evidence) и правило (если применимо).
- Для каждого риска описать воспроизводимую проверку (steps) по правилам (OUT-1, SEC-1, API-1, REL-1, OBS-1).
- Проверить, что структура ответа соответствует OUT-1 и содержит ≤3 рисков; соблюдены QA-1 и SCOPE-1.
- Проверить наличие всех обязательных файлов; зафиксировать запуск `make install` и `make test` (результаты будут подтверждаться вручную на этапе п.4–5 README).

## 8. Definition of Done

- Обязательные файлы присутствуют и заполнены последовательно; в каждом — «Как использовали AI» с ссылкой на `prompts.md`.
- В `prompts.md` обновлён «Master Prompt v1», достаточный для повторения запуска 2 на `TRAINING_PR.diff`.
- Чек-листы из Раздела 4 отражены в артефактах; проверки из Раздела 7 описаны; не добавлены новые правила вне SEC-1..QA-1; соблюдены OBS-1 и SCOPE-1.

## 9. Context Pack (для запуска 2)

Факты и правила (CASE.md):
- SEC-1: перед отправкой во внешний LLM из diff удаляются токены, пароли и приватные ключи.
- API-1: diff длиннее 20 000 символов отклоняется с HTTP 413.
- REL-1: внешний LLM-вызов имеет timeout 10 секунд; ошибка превращается в контролируемый ответ.
- OUT-1: ответ содержит `summary`, `risks` (≤3 с `file`, `line`, `evidence`, `risk`) и `checks`.
- SCOPE-1: сервис только советует; он не пишет код и не выполняет действия в GitHub.
- QA-1: риск включается в ответ только при подтверждении строкой diff или правилом.
- OBS-1: в лог пишутся только `request_id`, длительность и статус; содержимое diff и ответа модели не логируется.

Примеры:
- Хороший: «app/review_service.py:16 — diff отправляется во внешний LLM без удаления секретов, что нарушает SEC-1. Проверка: передать diff с тестовым token и убедиться, что в prompt осталось [REDACTED].»
- Плохой: «Код можно улучшить. Добавьте тесты и обработку ошибок.»

Границы: Forbidden: approve, merge, edit. Не придумывай правила. Flow: candidate → evidence → check. Нет evidence → пропусти.
