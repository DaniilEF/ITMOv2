# SDD в существующем проекте

**Практика 5 · OpenSpec в brownfield · 90 минут**

- **Часть 1:** проводим одну фичу через полный цикл.
- **Часть 2:** настраиваем OpenSpec и сравниваем форму до/после.

Ведущий делает → студенты повторяют → проверяем результат.

---

## Общий цикл OpenSpec

Часть 1 — полный цикл фичи. Часть 2 — настройка формы specs/design.

| Этап | Действие |
|---|---|
| **Артефакты** | Цель и требования; design и задачи |
| **Review** | Человек уточняет и согласует план |
| **Apply** | Агент меняет код по плану |
| **Проверки** | Tests и diff; приёмка человеком |
| **Archive** | Фиксируем итог и обновляем specs |

**Последовательность:** Explore → propose → human review → apply → tests / acceptance → sync / archive.

При ошибке или новом понимании возвращаемся к решению человека и review. Архивируем **после приёмки**.

Сначала делаем намерение и границы изменения видимыми. Артефакты можно уточнять по мере понимания задачи.

---

## Что делает OpenSpec, а что — модель

CLI собирает инструкции и статус. Содержание изменения создаёт модель в coding client.

| Участник | Роль |
|---|---|
| **Человек** | Задаёт цель, поручает работу, принимает итог |
| **Агент: client + model** | Читает инструкции, пишет текст и код |
| **Документы и код** | `proposal`, `specs`, `tasks`, `design` (если нужен), код и tests |
| **OpenSpec CLI (без LLM)** | `status`, `instructions`, `validate`; инструкции и проверка структуры |
| **Файлы проекта** | `schema`, `config`, `artifacts` |
| **Проверка** | Runner выполняет tests/diff; человек выполняет review |

**Приёмка — человек. Текст — модель.**

Готово: различаем решение человека, генерацию модели и детерминированные операции CLI. Человек задаёт и принимает поведение; модель пишет; CLI и runner выполняют свои проверки.

## Перед стартом · Устанавливаем OpenSpec

В корне своего проекта. **Node.js ≥ 20.19.0**; свои код, правила, tools и tests сохраняем.

Терминал проекта:

```bash
node --version
npm install -g @fission-ai/openspec@1.14.1
openspec --version
openspec init --profile core
```

В `init` выберите свой coding client; `core` даёт нужные шесть workflow. Перезагрузите клиент. В шагах видны OpenCode-команды и реальные имена Codex skills.

Затем попросите агента выполнить:

```bash
openspec --version
openspec list --json
```

**Готово:** агент видит OpenSpec 1.14.1 и правильный корень вашего проекта.

## Десять небольших фич для своего проекта

Выберите одну полезную идею; новый backend, продукт или framework не требуется.

| Контент и интерфейс | Ввод и действия |
|---|---|
| 1. Фильтр существующего списка | 6. Проверка существующего ввода |
| 2. Поиск по имеющемуся контенту | 7. Экспорт видимых данных в файл |
| 3. Сортировка существующих элементов | 8. Одна локальная настройка |
| 4. Сброс фильтров или настроек | 9. Клавиша для существующего действия |
| 5. Копирование ссылки или результата | 10. Предпросмотр существующего изменения |

**Готово:** выбрана одна фича; дальше запишем 3–5 условий и то, что сохраняем.

## Шаг 1. Выбираем фичу, исследуем и обсуждаем

Небольшое улучшение своего проекта: фильтр, сортировка, поле ответа или проверка входа.

**OpenCode** (`Codex: $openspec-explore`):

```text
/opsx-explore
Хочу [небольшая фича моего проекта].
Прочитай затронутый код и существующие тесты.
Что уже есть? Что спорно или лишнее?
Найди команду проверки и запусти baseline.
Предложи узкие границы и вопросы для меня.
Код пока не меняй.
```

Проверьте идею по коду: что уже есть и что можно упростить. Запишите **3–5 условий приёмки** и старое поведение, которое сохраняем.

**Готово:** выбрана фича; записаны 3–5 условий и то, что должно продолжить работать.

## Шаг 2. Создаём спецификацию

Замените `my-feature` коротким именем своей фичи.

**OpenCode** (`Codex: $openspec-propose`):

```text
/opsx-propose my-feature
Цель: [одна фича моего проекта].
Используй выводы explore и принятые решения.
Зафиксируй 3–5 условий, ошибки и границы.
Сохрани согласованное прежнее поведение.
Укажи, что не входит в изменение.
Подготовь документы. Остановись до apply.
```

Передайте решения шага 1: цель, условия, ошибки и границы. Прочитайте предложение до разрешения на код.

**Готово:** предложение описывает нужное поведение и способ его проверить.

## Как посмотреть созданные specs и changes

`CHANGE` и `SPEC` — реальные имена из списка, а не слова для буквального запуска.

**CLI · терминал своего проекта:**

```bash
openspec list
openspec list --specs
openspec show CHANGE --type change
openspec validate CHANGE --type change \
  --strict --no-interactive
openspec view
```

`CHANGE` берите из `list`; `SPEC` — из `list --specs`.

Если `SPEC` есть в списке:

```bash
openspec show SPEC --type spec
```

`validate` проверяет документы; `view` — разовый текстовый обзор.

**Готово:** выбран реальный change. Пустой список main specs до первого archive — нормально.

## Шаг 3. Проверяем и уточняем решение

Сначала отдельный проверяющий чат или агент. Затем решение человека.

**Проверяющий чат:**

```text
Прочитай предложение my-feature и связанный код.
Проверь цель, допущения, ошибки и совместимость.
Покажи конкретные пробелы. Файлы не меняй.
```

**Если нужно уточнение — основной чат OpenCode:**

```text
/opsx-update my-feature
Учти согласованное решение: [уточнение].
```

Разберите замечания; не требуйте выдуманных ошибок.

В Codex уточнение вызывает `$openspec-update-change my-feature`.

**Готово:** вопросы разобраны; вы прочитали итог и разрешили apply.

## Шаг 4. Реализуем фичу

Запускайте apply после принятия спецификации.

**OpenCode** (`Codex: $openspec-apply-change`):

```text
/opsx-apply my-feature
Реализуй согласованное изменение.
Используй архитектуру и проверки проекта.
Не расширяй границы задачи.
При новом решении сначала обсуди его со мной.
Покажи изменения и результаты проверок.
Остановись до archive.
```

Следите за границами задачи. Если spec неверна или появились новые факты — остановите код и согласуйте правку.

Обновите документы через `/opsx-update my-feature` (Codex: `$openspec-update-change my-feature`). Прочитайте и примите diff; затем apply и проверки.

**Готово:** есть код, просмотренные изменения и фактические результаты проверок.

---

## Шаг 5. Проверяем и принимаем результат

Используйте настоящую команду проверки своего проекта.

**Отдельный проверяющий чат / агент:**

```text
Прочитай требования my-feature и изменения.
Найди и запусти команду проверки этого проекта.
Проверь основной, ошибочный и старый сценарии.
По каждому: ожидание → факт → доказательство.
Файлы не меняй.
Не считай отчёт автора самостоятельной проверкой.
```

Разберите результат независимой проверки и исправьте существенное. Человек сопоставляет условия и факт; к шагу 6 переходим после приёмки.

**Готово:** условия проверены; вы можете объяснить, почему принимаете фичу.

---

## Шаг 6. Обновляем specs и архивируем

Только после приёмки человеком.

**OpenSpec · чат OpenCode:**

```text
/opsx-sync my-feature
Покажи diff текущей спецификации.
Сверь её с принятым поведением.
/opsx-archive my-feature
Покажи main specs и запись в archive.
```

Проверьте, что main spec описывает принятое поведение.

В Codex: `$openspec-sync-specs`, затем `$openspec-archive-change`.

**Готово:** текущая спецификация актуальна, завершённое изменение сохранено в истории.

## Часть 2. Настраиваем OpenSpec под себя

**77–90 мин.** Один раз задаём правило проекта; проверяем его на одном фрагменте.

| Сейчас | Готово, когда |
|---|---|
| 1. Сохраним фрагмент «до» и постоянное правило проекта | Правило остаётся в config для следующих изменений |
| 2. Проверим действие правила на этом фрагменте | Diff принят человеком; смысл фрагмента сохранён |

Шаг 7 — исходный фрагмент и правило. Шаг 8 — преобразование и проверка.

---

## Шаг 7. Добавляем правило OpenSpec для проекта

Один раз сохраняем правило проекта; OpenSpec включает его в будущие инструкции.

**OpenCode** (`Codex: $openspec-propose`):

```text
/opsx-propose my-next-feature
Цель: [связанная фича]. Остановись до apply.
```

Сохраните существующий фрагмент «до». Объедините с текущим `openspec/config.yaml`:

```yaml
rules:
  design:
    - Объясни взаимодействие диаграммой Mermaid.
```

Дополните текущий `rules`; второй `rules` не создаём. Правило действует для будущих `design` проекта; `design` нужен не всегда.

Если `design` нет: `rules.specs` и Given/When/Then для существующей spec.

**Готово:** правило сохранено для будущих design; фрагмент «до» нужен для проверки.

---

## Шаг 8. Меняем форму и проверяем смысл

Сначала свежие инструкции, затем предлагаемый diff и подтверждение человека.

**OpenCode** (`Codex: $openspec-update-change`):

```text
/opsx-update my-next-feature
Перед правкой выполни в shell:
openspec instructions design --change my-next-feature --json
Проверь в ответе моё актуальное правило.
Примени его к тому же фрагменту; покажи diff.
Сохрани смысл и границы; правь после подтверждения.
Код не меняй.
```

Для spec: в CLI укажите `specs`, в config — `rules.specs`; назовите свой файл.

После подтверждения сравните до/после; Mermaid откройте как диаграмму.

**Готово:** правило проверено на одном draft и остаётся для следующих изменений проекта.

## ДЗ 5 · Две команды — одна фича

Выберите другой SDD-фреймворк и согласуйте две спецификации **до генерации кода**.

**Эмуляция работы двух команд · два чата:**

| Команда 1 — спека UI | Команда 2 — спека логики |
|---|---|
| Экраны и действия | Данные и алгоритм |
| Состояния и ошибки | Правила и API |

### Согласуйте общий контракт

Сверьте данные, вызовы, ошибки и состояния. Примите решения и обновите обе спеки.

**После согласования:** реализация → сквозной сценарий и проверка ошибки / границы.

### Оценивание

| За что | Содержание | Баллы |
|---|---|---:|
| Другой SDD-фреймворк | Применение и сравнение с OpenSpec | 2 |
| Две спецификации | UI и логика, согласованные до кода | 2 |
| Реализация | Работающие UI и логика, сквозные проверки | 5 |
| Рефлексия | Что согласовали и чему научились | 1 |
| **Итого** | **Максимум** | **10** |

**Сдача:** спеки до/после, общий контракт, код, проверки и короткое демо.

*Решения принимает человек.*
