# Рефлексия: SpecKit vs OpenSpec

- Процесс и инструменты: SpecKit ставится как Specify CLI и работает через интеграции с агентами (команды вида /speckit.* и `specify`), предоставляет готовые workflow (specify, plan, tasks, implement, converge). OpenSpec тоже даёт CLI и пошаговый цикл (explore → propose → review → apply → tests/acceptance → sync/archive), но сильнее фиксирует этапы и роли (человек/агент/CLI/runner) и чёткие правила проекта.
- Структура артефактов: в SpecKit артефакты по умолчанию — spec.md, plan.md, tasks.md + workflow отчёты; мы дополнительно использовали YAML-спеки (ui/logic/contract) для явного контракта. В OpenSpec акцент на CHANGE/SPEC и правила проекта (rules.design/specs), с последующим `sync` и `archive` — сильнее выражен жизненный цикл спецификаций.
- Согласование UI ↔ логика: разделение на `ui.spec.yaml`, `logic.spec.yaml` и общий `contract.spec.yaml` в SpecKit-подходе предотвращает расхождения; `uses:` обеспечивает единый источник истины. В OpenSpec согласование чаще происходит в одном CHANGE/SPEC с человеческим ревью и `view/validate`, а консолидация — на шаге `sync`.
- Проверки и валидация: у используемой версии Specify CLI нет команды `validate` для наших YAML, поэтому применили локальную YAML/схемную проверку и ручные e2e-проверки UI; для консистентности можно подключать `speckit.analyze`. В OpenSpec есть явная `openspec validate` для документов и дисциплина «ожидание → факт → доказательство», что снижает риск разрыва между намерением и реализацией.
- Порог входа и гибкость: SpecKit гибко комбинирует процессы, расширяется через presets/extension/workflow и быстро интегрируется с агентами; OpenSpec задаёт более «жёсткий каркас» с правилами (SEC-1..QA-1) и архивированием, что полезно для командной дисциплины и трассируемости.
- Когда что выбирать: для быстрых учебных фич с упором на интеграцию агента и собственный формат спек — удобнее SpecKit; для командной работы с обязательным контролем формы результата, синхронизацией и историей — OpenSpec.
